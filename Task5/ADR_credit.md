### **Название задачи:**
Реализация онлайн-подачи заявок на кредит через интернет-банк и сайт банка «Стандарт» с предодобренными предложениями и ускоренной обработкой

### **Автор:**
Команда цифровой трансформации

### **Дата:**
16.05.2026

### **Контекст**
После запуска MVP онлайн-открытия депозитов банк «Стандарт» планирует цифровизацию кредитного направления в течение года. Кредиты создают основной поток средств для банка, поэтому автоматизация кредитного процесса — критически важная задача.

**Текущее состояние:**
- Клиент может подать заявку на кредит только в отделении через АБС.
- Заявки попадают из АБС в Кредитный конвейер через интеграцию по БД **раз в сутки**.
- Скоринг происходит в Кредитном конвейере: вызывается система кредитного скоринга, которая использует данные из Бюро кредитных историй (онлайн), АБС и Кредитного конвейера (данные загружаются раз в сутки).
- Решение о выдаче принимает сотрудник отдела кредитования на основе скоринга и параметров заявки.
- При одобрении информация передаётся в АБС раз в сутки для зачисления средств.

**Целевое состояние (через год):**
- Новый клиент может подать заявку на кредит на сайте и получить мгновенное решение (если предоставлены паспортные данные).
- Существующий клиент видит предодобренные предложения в интернет-банке и может подать заявку с СМС-подтверждением.
- Предодобренные заявки обрабатываются в течение рабочего дня (а не недели).
- Клиент получает СМС-уведомления об изменении статуса заявки.
- Менеджер в отделении может продолжить работу с заявкой, поданной через сайт.

**Ключевые ограничения:**
- Обмен между АБС и Кредитным конвейером через БД — не чаще раза в сутки (+R4).
- Система скоринга не должна нагружаться предрасчётами в рабочее время (+R7, P4).
- Кредитный конвейер и система скоринга поддерживают горизонтальное масштабирование и 24/7 (P6).
- Те же нефункциональные требования, что и для депозитного процесса (NFR1–NFR15 из ADR_deposit).

#### Обоснование архитектурных решений

**1. Новый Сервис кредитов как отдельный микросервис (Java Spring Boot + PostgreSQL)**

*Почему:*
- Аналогично Сервису депозитов (ADR_deposit): изоляция от монолита интернет-банка, независимое масштабирование (NFR_C5, NFR_C9)
- Java Spring Boot — существующая экспертиза банка (система кол-центра, команда АБС с Java-специалистами) (NFR_C10)
- PostgreSQL — знакомая технология (кол-центр, скоринг), не нагружает Oracle БД АБС (NFR_C4)
- Сервис кредитов и Сервис депозитов — отдельные микросервисы с раздельным доступом (NFR_C14)
- Горизонтальное масштабирование независимо от других систем (NFR_C5)

**2. Модуль кредитов как SPA на React.js, встраиваемый в интернет-банк**

*Почему:*
- Аналогично модулю депозитов: избегает доработок ядра монолита интернет-банка (NFR_C9)
- React.js уже используется в банке — есть экспертиза (NFR_C10)
- Современный UX с быстрым откликом, корпоративный дизайн (NFR_C2, NFR_C12)
- Независимый цикл разработки и деплоя от монолита

**3. Альтернативный канал в Кредитный конвейер через Kafka (в обход ежедневной синхронизации БД)**

*Почему:*
- Ежедневная синхронизация БД АБС → Кредитный конвейер не позволяет обработать предодобренные заявки в тот же день (NFR_C17, NFR_C18)
- Кредитный конвейер на Camunda поддерживает горизонтальное масштабирование и 24/7 — готов к онлайн-нагрузке (NFR_C19)
- Kafka обеспечивает гарантированную доставку заявок (NFR_C7)
- Сервис кредитов отправляет предодобренные заявки напрямую в Kafka → Кредитный конвейер, минуя АБС
- Camunda позволяет реализовывать обработчики на Java — можно добавить consumer для Kafka без изменения ядра системы
- В банке есть Java-экспертиза для доработки обработчиков Camunda (NFR_C10)

**4. Онлайн-скоринг через REST API системы скоринга (для сайта и интернет-банка)**

*Почему:*
- Система скоринга уже имеет REST API на Flask — готовый интерфейс для интеграции (NFR_C10)
- Для сайта: мгновенное решение по кредиту при наличии паспортных данных (UC_C2) — вызов скоринга онлайн с данными из Бюро кредитных историй
- Для интернет-банка: упрощённый повторный скоринг при подаче заявки по предодобренному предложению (UC_C4)
- Система скоринга поддерживает горизонтальное масштабирование и 24/7 — готова к дополнительным вызовам (NFR_C19)
- Данные из АБС для скоринга берутся из кэша Сервиса кредитов (обновляются через Kafka), а не прямыми запросами к АБС (NFR_C4)

**5. Ночной batch-расчёт предодобренных предложений (вне рабочих часов)**

*Почему:*
- Система скоринга испытывает повышенную нагрузку в рабочие часы и не должна использоваться для предрасчётов днём (NFR_C16)
- Ночью (например, 01:00–05:00) нагрузка на скоринг минимальна — batch-процесс не мешает основной работе
- Предодобренные предложения рассчитываются для активных клиентов интернет-банка — ограниченное множество
- Результаты сохраняются в PostgreSQL Сервиса кредитов — быстрый доступ днём без вызова скоринга (NFR_C2)
- При подаче заявки — упрощённый повторный скоринг (проверка, что ситуация не изменилась), а не полный перерасчёт

**6. Асинхронная интеграция с АБС через Kafka + расширение Адаптера АБС**

*Почему:*
- Аналогично депозитному процессу (ADR_deposit): БД АБС перегружена, прямые онлайн-запросы недопустимы (NFR_C4)
- Существующий Адаптер АБС (Java-сервис) расширяется для поддержки кредитных заявок — нет необходимости в новом сервисе
- Kafka буферизует заявки и защищает АБС от пиковых нагрузок (NFR_C7, NFR_C8)
- Адаптер АБС работает с выделенными таблицами в Oracle БД — не затрагивает существующий Delphi/PL-SQL код

**7. Менеджер отделения видит предварительные заявки из онлайн-каналов в АБС**

*Почему:*
- Клиент мог получить предварительное одобрение на сайте — менеджер должен продолжить работу с той же заявкой (UC_C5, F15)
- Адаптер АБС записывает заявки из Сервиса кредитов в Oracle БД — менеджер видит их в десктоп-клиенте АБС
- Нет необходимости дорабатывать АБС — заявки появляются в новых таблицах, доступных через существующий интерфейс
- Разделение доступа сохраняется: менеджеры депозитов не видят кредитные данные (NFR_C14)

**8. СМС-уведомления об изменении статуса заявки на кредит**

*Почему:*
- Бизнес требует информирования клиента о каждом изменении статуса (F17, UC_C8)
- Сервис кредитов работает с СМС-шлюзом напрямую (аналогично Сервису депозитов) — без доработки ядра интернет-банка (NFR_C9)
- Статусы поступают из Кредитного конвейера через Kafka — асинхронно, без онлайн-зависимости

### **Альтернативы**

**A1. Передача предодобренных заявок в Кредитный конвейер через ежедневную синхронизацию БД (без Kafka)**

| Критерий | Описание |
|----------|----------|
| Суть | Предодобренные заявки записываются в АБС и попадают в Кредитный конвейер через существующий ежедневный обмен по БД |
| Плюсы | Нет необходимости дорабатывать Кредитный конвейер для приёма заявок из Kafka; используется существующий механизм |

| Решение | **Отклонено** — нарушает NFR_C17, NFR_C18, NFR_C4 |

| Критерий | Описание |
|----------|----------|
| Суть | Сервис кредитов вызывает систему скоринга для предрасчёта предодобренных предложений в течение рабочего дня |
| Плюсы | Предодобренные предложения всегда актуальны; нет необходимости в batch-процессе |
| Минусы | Система скоринга испытывает повышенную нагрузку в рабочие часы — предрасчёты усугубят проблему; нарушение прямого требования бизнеса (NFR_C16, P4, +R7); риск деградации скоринга для активных заявок |
| Решение | **Отклонено** — нарушает NFR_C16, P4, +R7 |

**A3. Реализация кредитного функционала внутри монолита интернет-банка**

| Критерий | Описание |
|----------|----------|
| Суть | Доработать существующий монолит ASP.NET MVC для приёма заявок на кредит и отображения предодобренных предложений |
| Плюсы | Нет необходимости в новых сервисах; единая кодовая база |
| Минусы | Зависимость от подрядчика для обновления ядра (NFR_C9); .NET Framework 4.5 несовместим с Kafka (NFR_C11); нет горизонтального масштабирования (NFR_C5); высокий риск для стабильности существующего функционала |
| Решение | **Отклонено** — нарушает NFR_C5, NFR_C9, NFR_C11 (аналогично A2 из ADR_deposit) |

**A4. Прямой вызов REST API Кредитного конвейера вместо Kafka**

| Критерий | Описание |

| Суть | Сервис кредитов вызывает REST API Кредитного конвейера синхронно для передачи предодобренных заявок |
| Плюсы | Проще в реализации, нет необходимости настраивать Kafka-топики для кредитного конвейера; мгновенная передача заявки |
| Минусы | Нет гарантированной доставки — при недоступности Кредитного конвейера заявка теряется (NFR_C7); нет буферизации — пиковая нагрузка напрямую воздействует на Кредитный конвейер; нарушение изоляции отказов (NFR_C8); не соответствует стратегии банка по использованию Kafka (NFR_C11) |
| Решение | **Отклонено** — нарушает NFR_C7, NFR_C8, NFR_C11 |

**A5. Хранение предодобренных предложений в АБС вместо Сервиса кредитов**

| Критерий | Описание |
|----------|----------|
| Суть | Результаты ночного скоринга записываются в Oracle БД АБС, интернет-банк запрашивает их через API |
| Плюсы | Единый источник данных в основной банковской системе |
| Минусы | Дополнительные записи и чтения из перегруженной БД АБС (NFR_C4); онлайн-зависимость от АБС для отображения предодобренных предложений; сбой АБС = недоступность предодобренных предложений (NFR_C8); ночной batch записывает большое количество данных в АБС — риск для стабильности |
| Решение | **Отклонено** — нарушает NFR_C4, NFR_C8. Предодобренные предложения хранятся в PostgreSQL Сервиса кредитов |

**A6. Отдельный микросервис для скоринга вместо прямого вызова системы скоринга**

| Критерий | Описание |
|----------|----------|
| Суть | Создать промежуточный сервис-агрегатор для вызова системы скоринга, кэширования результатов и управления нагрузкой |
| Плюсы | Дополнительный слой защиты системы скоринга от перегрузки; возможность тонкого управления кэшированием и rate limiting |
| Минусы | Избыточная сложность: Сервис кредитов уже кэширует результаты скоринга (предодобренные предложения); дополнительный сервис — дополнительная инфраструктура и поддержка; система скоринга уже имеет REST API и поддерживает горизонтальное масштабирование |
| Решение | **Отклонено** — достаточно прямого вызова из Сервиса кредитов с ночным batch и кэшированием |

**Недостатки, ограничения, риски**

| № | Риск / Ограничение | Описание | Митигация |
|---|-------------------|----------|-----------|
| R_C1 | Доработка Кредитного конвейера для приёма заявок из Kafka | Кредитный конвейер на Camunda сейчас получает заявки через ежедневную синхронизацию БД. Необходимо добавить Kafka-consumer для приёма предодобренных заявок в реальном времени | Camunda позволяет реализовывать обработчики на Java — добавить consumer технически возможно. В IT-отделе есть специалисты, которые могут менять обработчики Camunda. Начать с минимальной реализации: один consumer для одного топика |
| R_C2 | Ночной batch-расчёт может не успеть завершиться до начала рабочего дня | При большом количестве активных клиентов интернет-банка batch-процесс скоринга может занять несколько часов. Если процесс не завершится к утру, предодобренные предложения будут неактуальны | Ограничить batch активными клиентами интернет-банка (не все клиенты банка); распараллелить вызовы скоринга (batch-обработка чанками); настроить мониторинг длительности batch; при необходимости — увеличить горизонтальное масштабирование системы скоринга ночью |
| R_C3 | Рассинхронизация данных между Сервисом кредитов и АБС | Данные о клиентах для скоринга кэшируются в Сервисе кредитов и обновляются асинхронно через Kafka. Возможна задержка между изменением данных в АБС и их отражением в Сервисе кредитов | Для ночного batch это допустимо — данные обновляются в течение дня. При подаче заявки — упрощённый повторный скоринг с актуальными данными из Бюро кредитных историй. Критичные данные (остатки на счетах) обновляются с минимальной задержкой |
| R_C4 | Нагрузка на систему скоринга от онлайн-вызовов | Помимо ночного batch, Сервис кредитов вызывает скоринг онлайн: для мгновенных решений с сайта (UC_C2) и упрощённого повторного скоринга из интернет-банка (UC_C4) | Упрощённый скоринг для предодобренных заявок — минимальный набор данных; система скоринга поддерживает горизонтальное масштабирование (NFR_C19); мониторинг нагрузки и автоматическое масштабирование; rate limiting на стороне Сервиса кредитов |
| R_C5 | Расширение Адаптера АБС для кредитных заявок | Адаптер АБС изначально создан для депозитных заявок (ADR_deposit). Необходимо добавить поддержку кредитных заявок — новые таблицы, новые топики Kafka | Адаптер АБС спроектирован как расширяемый Java-сервис. Кредитные заявки — новые таблицы в Oracle БД и новые топики Kafka. Не затрагивает существующий депозитный функционал. Разделение доступа на уровне таблиц/схем Oracle (NFR_C14) |
| R_C6 | Идентификация клиента: заявка с сайта → визит в отделение | Новый клиент получает предварительное решение на сайте, но обязан прийти в отделение для идентификации (+R1). Менеджер отделения должен найти и продолжить работу с этой заявкой | Заявки с сайта записываются Адаптером АБС в Oracle БД с уникальным идентификатором. Менеджер ищет заявку по Ф.И.О. и телефону в АБС. В будущем — QR-код в СМС для быстрого поиска заявки |
| R_C7 | Безопасность передачи паспортных данных через сайт | При подаче заявки на кредит с сайта клиент передаёт паспортные данные — чувствительная информация, требующая защиты | TLS/SSL шифрование для всех каналов (NFR_C3); шифрование данных в PostgreSQL Сервиса кредитов; минимальное время хранения паспортных данных; соответствие требованиям регулятора по защите ПДн |
| R_C8 | Один ЦОД для Сервиса кредитов на старте | Аналогично Сервису депозитов: интернет-банк работает в одном ЦОД, резервный ЦОД требует настройки | Развернуть Сервис кредитов с поддержкой горизонтального масштабирования; подготовить конфигурацию для развёртывания в резервном ЦОД; настроить репликацию PostgreSQL; план переключения на резервный ЦОД (NFR_C6) |
| R_C9 | Скоринг для новых клиентов с сайта использует только данные Бюро кредитных историй | Для нового клиента нет данных в АБС — скоринг основан только на данных из Бюро кредитных историй. Это может снизить точность оценки | Для MVP это допустимо — решение является предварительным. Финальное решение принимается в Кредитном конвейере после идентификации в отделении с полным набором данных. Система скоринга поддерживает разные модели для разных сценариев |
| R_C10 | Интеграция Кредитного конвейера с Kafka требует координации с подрядчиком | Кредитный конвейер — коробочное решение на базе Camunda, частично дорабатывается подрядчиком. Добавление Kafka-consumer может потребовать согласования | В IT-отделе банка есть специалисты, которые могут менять обработчики и бизнес-процессы в Camunda. Kafka-consumer — это внешний обработчик, не изменяющий ядро Camunda. Согласовать с подрядчиком стандартный механизм расширения |
