#### Обоснование архитектурных решений

**1. Новый Сервис депозитов как отдельный микросервис (вне монолита интернет-банка)**

*Почему:*
- Монолит интернет-банка привязан к платформе подрядчика — обновление ядра зависит от него (NFR9)
- Текущий стек (.NET Framework 4.5) несовместим с Kafka (NFR11)
- В банке есть Java-экспертиза: команда АБС имеет специалистов с Java-опытом (NFR10)
- Горизонтальное масштабирование нового сервиса независимо от монолита (NFR5)
- Изоляция отказов: сбой монолита не блокирует депозитный функционал и наоборот (NFR8)
- Это первый шаг к микросервисной архитектуре интернет-банка (NFR13)

**2. Java Spring Boot для Сервиса депозитов**

*Почему:*
- В банке уже есть Java-экспертиза (команда АБС, система кол-центра на Spring Boot)
- Совместимость с Kafka (нативная поддержка через Spring Kafka)
- Spring Boot — проверенный стек для микросервисов, уже используется в системе кол-центра
- PostgreSQL — знакомая технология (используется в системе кол-центра и скоринга)

**3. Асинхронная интеграция с АБС через Kafka + отдельный Адаптер АБС**

*Почему:*
- БД АБС перегружена — прямые онлайн-запросы недопустимы (NFR4)
- Kafka обеспечивает гарантированную доставку заявок — защита от потери (NFR7)
- Буферизация заявок в Kafka защищает АБС от пиковых нагрузок (NFR8 — изоляция отказов)
- Kafka — стратегический выбор банка на перспективу (NFR11)
- Адаптер АБС — отдельный Java-сервис **вне контура АБС**, работает с Oracle через JDBC. Не требует изменений в Delphi/PL-SQL коде АБС
- Java-экспертиза в банке есть (команда АБС может работать с системой кол-центра на Java)

**4. Модуль депозитов как SPA на React.js, встраиваемый в интернет-банк**

*Почему:*
- Избегает доработок ядра монолита интернет-банка (NFR9)
- React.js уже используется в банке (сайт, система кол-центра) — есть экспертиза
- Позволяет реализовать современный UX с быстрым откликом (NFR2)
- Легко поддерживать корпоративный дизайн (NFR12)
- Независимый цикл разработки и деплоя от монолита

**5. Сервис ставок как отдельный компонент внутри Сервиса депозитов**

*Почему:*
- Ставки сейчас в Excel — нужен централизованный источник (единая точка правды)
- Разделение доступа: бэк-офис депозитов и кредитов работают со ставками через API, не имея прямого доступа к данным друг друга (NFR14)
- Персонализированные ставки кэшируются — не нагружают АБС при каждом запросе (NFR2, NFR4)
- Ежедневное обновление из АБС через Kafka — асинхронно, без онлайн-запросов

**6. PostgreSQL для Сервиса депозитов**

*Почему:*
- Уже используется в банке (система кол-центра, система скоринга) — есть экспертиза
- Не нагружает Oracle БД АБС (NFR4)
- Подходит для микросервисной архитектуры (database-per-service pattern)
- Поддерживает горизонтальное масштабирование через репликацию (NFR5)

### **Альтернативы**
Опишите здесь наиболее важные альтернативные решения.

**A1. Интеграция интернет-банка с АБС напрямую через REST API (вместо Kafka)**

| Критерий | Описание |
|----------|----------|
| Суть | Интернет-банк вызывает REST API АБС синхронно для подачи заявок |
| Плюсы | Проще в реализации, нет необходимости разворачивать Kafka |
| Минусы | БД АБС перегружена — прямые вызовы усугубят проблему; нет гарантированной доставки; сбой АБС блокирует подачу заявок; не соответствует стратегии банка (Kafka) |
| Решение | **Отклонено** — нарушает NFR4, NFR7, NFR8, NFR11 |

**A2. Реализация депозитного функционала внутри монолита интернет-банка**

| Критерий | Описание |
|----------|----------|
| Суть | Доработать существующий монолит ASP.NET MVC для приёма заявок на депозит |
| Плюсы | Нет необходимости в новых сервисах; единая кодовая база |
| Минусы | Зависимость от подрядчика для обновления ядра; .NET Framework 4.5 несовместим с Kafka; нет горизонтального масштабирования; высокий риск для стабильности существующего функционала |
| Решение | **Отклонено** — нарушает NFR5, NFR9, NFR11 |

**A3. Хранение ставок в АБС (Oracle) вместо Сервиса депозитов**

| Критерий | Описание |
|----------|----------|
| Суть | Реализовать управление ставками полностью в АБС, Сервис депозитов запрашивает ставки через API |
| Плюсы | Единый источник данных в основной банковской системе |
| Минусы | Дополнительные запросы к перегруженной БД АБС; онлайн-зависимость от АБС для отображения ставок; сбой АБС = недоступность ставок на сайте и в интернет-банке |
| Решение | **Отклонено** — нарушает NFR4, NFR8. Ставки кэшируются в Сервисе депозитов и обновляются асинхронно |

**A4. Использование MS SQL вместо PostgreSQL для Сервиса депозитов**

| Критерий | Описание |
|----------|----------|
| Суть | Использовать MS SQL (уже используется в интернет-банке) |
| Плюсы | Соответствует существующей инфраструктуре интернет-банка |
| Минусы | MS SQL используется в монолите подрядчика — лицензионные ограничения; PostgreSQL уже используется в микросервисных системах банка (кол-центр, скоринг) и лучше подходит для нового микросервиса |
| Решение | **Отклонено** — PostgreSQL лучше соответствует микросервисной архитектуре и существующей экспертизе |

Необходимо корректно спроектировать схему таблиц и polling-механизм для обнаружения изменений | Адаптер — тонкий слой: только JDBC-операции с выделенными таблицами. | R6 | СМС-подтверждение без доработки ядра интернет-банка | Ядро интернет-банка содержит СМС-функционал, но его доработка зависит от подрядчика | Сервис депозитов работает с СМС-шлюзом напрямую, минуя ядро интернет-банка; зависимость от подрядчика устраняется |
| R7 | Нагрузка на АБС при обработке заявок бэк-офисом | На MVP заявки обрабатываются вручную в АБС; рост числа заявок может увеличить нагрузку на БД | Адаптер АБС записывает заявки в Oracle БД пакетно, контролируя темп; в финальной версии (через год) обработка будет автоматической, что снизит нагрузку |
| R8 | Один ЦОД для Сервиса депозитов на старте | Интернет-банк работает в одном ЦОД; Сервис депозитов может быть развёрнут аналогично | Развернуть Сервис депозитов с поддержкой горизонтального масштабирования; подготовить конфигурацию для развёртывания в резервном ЦОД; настроить репликацию PostgreSQL |
| R9 | Регуляторное ограничение: новые клиенты требуют идентификации в отделении | Полностью онлайн-открытие депозита для новых клиентов невозможно | На MVP это учтено: заявка с сайта → звонок кол-центра → визит в отделение. Для существующих клиентов интернет-банка — полностью онлайн |
