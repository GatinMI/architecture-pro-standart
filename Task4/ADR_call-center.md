### **Название задачи:**
Расширение MVP онлайн-открытия депозитов: предоставление доступа к ставкам по депозитам для кол-центра банка и партнёрского кол-центра

### **Автор:**
Команда цифровой трансформации

### **Дата:**
16.05.2026

### **Контекст**
После запуска маркетинговой кампании на текущих и новых клиентов ожидается рост звонков в кол-центр. Возрастным клиентам банка может быть непросто сориентироваться в новых процессах, и они захотят уточнить условия открытия депозита по телефону. Для качественного обслуживания операторы кол-центра (как собственного, так и партнёрского) должны иметь доступ к актуальным ставкам по депозитам.

|**№**|**Требование**|

| NFR_CC7 | Аутентификация партнёрского кол-центра на SFTP-сервере по SSH-ключам |

| NFR_CC9 | Использование существующих технологий банка (Java Spring Boot, PostgreSQL) |
| NFR_CC10 | Партнёрский кол-центр не имеет прямого API-доступа к системам банка — только SFTP |
| NFR_CC11 | Формат файлов ставок должен быть согласован с партнёрским кол-центром и документирован |
| NFR_CC12 | Обеспечение наблюдаемости (мониторинг, логирование, метрики) для SFTP-сервера и API ставок |

#### Обоснование архитектурных решений

**1. Система кол-центра банка получает ставки через REST API Сервиса депозитов**

*Почему:*
- Система кол-центра уже на Java Spring Boot — REST API нативен для этого стека
- Сервис депозитов уже хранит кэш ставок (из ADR_deposit) — нет дополнительных запросов к АБС (NFR_CC8)
- Быстрый отклик — данные из кэша, миллисекунды (NFR_CC4)
- TLS-шифрование обеспечивает безопасность передачи данных (NFR_CC1)
- API уже частично существует для передачи заявок с сайта — расширяется endpoint'ом для ставок

**2. SFTP-сервер для передачи ставок партнёрскому кол-центру**

*Почему:*
- Партнёрский кол-центр — внешняя система, не может делать API-вызовы к банку (NFR_CC10)
- Партнёр готов получать файлы — SFTP соответствует их возможностям
- SFTP обеспечивает шифрование передачи (SSH) — безопасность данных (NFR_CC2)
- Асинхронный процесс: файл формируется и выкладывается по расписанию, партнёр скачивает когда удобно
- Нет прямой интеграции между внешним партнёром и внутренними системами банка — изоляция

**3. Сервис экспорта ставок как компонент Сервиса депозитов**

*Почему:*
- Сервис депозитов — единственный источник актуальных ставок (единая точка правды)
- Экспорт — лёгкий фоновый процесс: чтение из кэша, формирование файла, загрузка на SFTP
- Java Spring Boot + JSch (или Apache MINA SSHD) — стандартные библиотеки для SFTP
- Не требует новых технологий — используется существующая Java-экспертиза банка (NFR_CC9)

**4. Формат файлов: CSV с согласованной схемой**

*Почему:*
- CSV — универсальный формат, поддерживается любой системой
- Прост для парсинга на стороне партнёрского кол-центра
- Содержит только базовые ставки по продуктам — нет чувствительных данных (NFR_CC5)
- Легко документировать и версионировать схему

**5. Развёртывание SFTP-сервера в DMZ-зоне инфраструктуры банка**

*Почему:*
- SFTP-сервер доступен извне (для партнёра) — должен быть в DMZ для безопасности
- Изолирован от внутренних систем банка — даже при компрометации SFTP внутренние системы защищены
- Доступ только по SSH-ключам — нет парольной аутентификации (NFR_CC7)
- Мониторинг и логирование подключений — наблюдаемость (NFR_CC12)

### **Альтернативы**

**A1. Прямой доступ системы кол-центра к БД АБС для чтения ставок**

| Критерий | Описание |
|----------|----------|
| Суть | Система кол-центра подключается напрямую к Oracle БД АБС для чтения ставок |
| Плюсы | Нет необходимости дорабатывать Сервис депозитов; данные напрямую из источника |
| Минусы | БД АБС перегружена — дополнительные запросы усугубят проблему; нарушение изоляции систем; кол-центр получает зависимость от АБС; нарушение требований безопасности (разделение доступа) |
| Решение | **Отклонено** — нарушает NFR_CC8, NFR4 (из ADR_deposit), +R2 (из FURPS) |

**A2. API для партнёрского кол-центра вместо SFTP**

| Критерий | Описание |
|----------|----------|
| Суть | Разработать REST API для партнёрского кол-центра с аутентификацией по API-ключам |
| Плюсы | Real-time доступ к ставкам; единый механизм для обоих кол-центров |
| Минусы | Партнёрский кол-центр не может делать API-вызовы (ограничение их системы); необходимо открывать API для внешнего доступа — дополнительные риски безопасности; требует доработок на стороне партнёра |
| Решение | **Отклонено** — невозможно по техническим ограничениям партнёра (NFR_CC10) |

**A3. Передача ставок партнёрскому кол-центру по электронной почте**

| Критерий | Описание |
|----------|----------|
| Суть | Автоматическая отправка файлов со ставками по электронной почте контактам партнёрского кол-центра |
| Плюсы | Не требует развёртывания SFTP-сервера; простая реализация |
| Минусы | Email не обеспечивает достаточного уровня безопасности для передачи данных; нет гарантированной доставки и контроля получения; ручная обработка на стороне партнёра; сложно автоматизировать |
| Решение | **Отклонено** — недостаточная безопасность и надёжность по сравнению с SFTP |

**A4. Отдельный микросервис для управления ставками кол-центров**

| Критерий | Описание |
|----------|----------|
| Суть | Создать отдельный сервис, который агрегирует ставки из Сервиса депозитов и предоставляет их кол-центрам |
| Плюсы | Полная изоляция нового функционала; независимое масштабирование |
| Плюсы | Избыточная сложность для простого кейса (чтение ставок из кэша); дополнительный сервис — дополнительная инфраструктура и поддержка; Сервис депозитов уже имеет endpoint для ставок |
| Минусы | Избыточная сложность для простого кейса; дополнительный сервис — дополнительная инфраструктура и поддержка; Сервис депозитов уже имеет endpoint для ставок |
| Решение | **Отклонено** — достаточно расширить существующий Сервис депозитов |

| R_CC1 | Задержка обновления ставок у партнёрского кол-центра | Партнёр получает ставки через файлы по расписанию, а не в реальном времени. | R_CC2 | Развёртывание и поддержка SFTP-сервера | SFTP-сервер — новая инфраструктура для банка. Требует настройки, мониторинга, управления SSH-ключами | Использовать стандартное ПО (OpenSSH); разместить в DMZ; настроить мониторинг; документировать процесс управления ключами |
| R_CC3 | Безопасность SFTP-сервера | SFTP-сервер доступен извне — потенциальная точка атаки | Размещение в DMZ; аутентификация только по SSH-ключам; ограничение IP-адресов партнёра; регулярный аудит ключей; мониторинг подозрительной активности |
| R_CC4 | Рассинхронизация ставок между кол-центром и Сервисом депозитов | Система кол-центра кэширует ставки локально; при обновлении ставок в Сервисе депозит кэш кол-центра может быть устаревшим | Реализовать webhook-уведомление от Сервиса депозитов при изменении ставок; TTL кэша в системе кол-центра — не более 15 минут |
| R_CC5 | Формат файлов ставок может потребовать изменений | При расширении депозитных продуктов формат CSV может потребовать доработок | Версионирование формата файлов; документирование схемы; обратная совместимость при изменениях; уведомление партнёра заранее |
| R_CC6 | Нагрузка на Сервис депозитов от запросов кол-центра | Кол-центр (200 операторов) может генерировать значительную нагрузку на API ставок | API ставок возвращает данные из кэша — минимальная нагрузка; при необходимости — реализовать кэширование на стороне системы кол-центра с webhook-инвалидацией |
| R_CC7 | Партнёрский кол-центр не скачивает файлы вовремя | Если партнёр не скачает файл, операторы будут работать с устаревшими ставками | Мониторинг скачивания файлов; уведомление ответственных при пропуске; SLA с партнёром по частоте обновления |
